# AI modules

Read this before touching `lpm-core/modules/ai/**` or anything that generates or
caches an AI artifact. Split out of `AGENTS.md`; the rules are unchanged.

- AI integration: `lpm-core/modules/ai/` holds a provider-neutral adapter layer. Get an adapter with `AiIntegration::getInstance()->getAdapter()` (or `getAdapter(AiIntegration::PROVIDER_X)`), check `isAvailable()` first, then call `generate(AiRequest)` → `AiResponse`. Build requests with `AiRequest::text($prompt, $system)` / `addUserMessage()` and shape structured output with `setResponseSchema([...])` (read it back via `AiResponse::getJson()`). Errors throw `AiException`; logging goes to `LPMLog::CH_AI`. Provider specifics (endpoint, payload format, finish reasons) belong in the adapter — currently `lpm-core/modules/ai/gemini/GeminiAdapter.php`, built over `symfony/http-client`. Settings are config constants (`AI_PROVIDER`, `AI_REQUEST_TIMEOUT`, `AI_GEMINI_*`), read only in the adapter's `create()`/`AiIntegration::getInstance()` — never in domain code. To add a provider: implement `AiAdapter`, add a `PROVIDER_*` constant and a branch in `AiIntegration::createAdapter()`.
- AI-generated artifacts: each one is built by a `*Builder` that owns the gates, the context sent to the model and the prompt (plus a `PROMPT_VERSION`, on cached artifacts only). Generation happens ONLY on an explicit user action (never on page render), failures are never persisted, and token usage is logged per call to `LPMLog::CH_AI`. Two kinds exist, and the caching rules below apply only to the first:
  - **Cached** — the artifact is stored and shown again on later page loads (the issue summary, `lpm-core/modules/ai/summary/`).
  - **One-shot draft** — the model's output is handed to the user to edit and becomes something else entirely (the test checklist, `lpm-core/modules/ai/checklist/`, whose draft the user edits and publishes as a comment; the issue draft, `lpm-core/modules/ai/draft/`, which fills in the new-issue form). Nothing is stored, so there is no `sourceHash` and nothing to invalidate; the builder additionally converts the response to the target format (`IssueTestChecklistBuilder::toCommentText()`).
- The project's domain context (what the product is, who it is for, the stack, the team's own terms) reaches the model through `Project::$aiContext` and is assembled in exactly ONE place — `AiProjectContext::block($project)`. A builder mixes it in with that single call and its own choice of where the block goes; it must never format, re-title or re-truncate the context itself, so the wording stays identical across artifacts and the size cap (`AI_PROJECT_CONTEXT_MAX_LENGTH`, validated on save in `ProjectService::saveProject()`) holds for every request. An empty context yields an empty string — emit nothing at all rather than a `(not set)` placeholder. The block is part of the request text, so `sourceHash` covers it automatically: editing a project's context invalidates that project's cached artifacts, and that is the intended behaviour.
- The issue's own state reaches the model through exactly ONE place too — `AiIssueContext::statusLine($issue, $notes)`. A builder must never assemble that line itself and must never fall back to the bare `Issue::getStatus()`: the state is named the way the user sees it (`IssueViewHelper::statusLabel()` — the substatus when the issue has one, the plain status otherwise), so an artifact cannot contradict the status badge on the page. Only the note that explains the substatus is per-artifact — the caller passes its own `SUBSTATUS_NOTES` map, because the summary and the test checklist need different things from the same state (whether the issue is finished, versus whether this is a first or a repeat test pass). Keep the rest of the issue block from restating what the status already says, so the request never carries two versions of the same fact. The line is part of the request text, so `sourceHash` covers it automatically: moving a sticker on the board or taking an issue for testing invalidates that issue's cached artifacts, and that is the intended behaviour.
- Cached AI artifacts are stored by a model over their own table (`IssueSummary` → `lpm_ai_issue_summary`, one row per issue, shared by all users). **Every cached AI artifact MUST have its own `sourceHash`** covering *exactly* what goes into the model, since the cached artifact is regenerated only when that hash differs. Hash the built request text itself rather than a hand-picked list of fields — `IssueSummaryBuilder::sourceHash()` is md5 over `PROMPT_VERSION` + system instruction + the same prompt `generate()` sends, so every input is covered automatically and nothing drifts as the prompt grows. A hand-written field list is where this goes wrong: it silently misses metadata that reaches the prompt indirectly (a project rename changes `projectName`) and in-place edits (`IssueService::resolveComment()` flips `REQUEST_CHANGES` → `REQUEST_CHANGES_RESOLVED` without touching comment ids or their count). This makes prompt building part of the hash contract: keep it free of side effects and of anything time- or random-dependent (logging belongs in `generate()`), because it runs on every page render. Bump `PROMPT_VERSION` for changes the request text does not capture — response schema, generation params.
